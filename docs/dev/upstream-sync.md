# Upstream sync ledger

Solverr is a standalone fork with two upstreams. This file is the single owner of one question: **what has been taken from each of them, through which commit, and what is deliberately different.** Nothing else records that, so an audit that does not update this file gets re-run from scratch next time.

Run `/upstream-audit` to refresh it. The reference clones are siblings of this repo, read-only:

| Upstream | Clone | Role |
|---|---|---|
| FlareSolverr | `../FlareSolverr` | The base. The Chrome engine, the `/v1` API, sessions, and most of the surrounding code come from here. |
| Byparr | `../Byparr` | The origin of the stealth stack (Camoufox via invisible_playwright plus playwright-captcha). |
| byparr-proxy | `../byparr-proxy` | Idea credit only for the passthrough. No code taken. |

## Deliberately different

Cite one of these instead of re-arguing it. Change one only when the owner asks.

- **A timeout is HTTP 500 in the FlareSolverr error shape**, not Byparr's 408. Required by the `/v1` contract. The same applies to an unreachable target, which Byparr now answers with 502 (`2852dc2`): the shape has one error status, and the controller already falls back to the other engine before any of this reaches a client.
- **`solution.contentType` is emitted only when the body is not HTML.** Byparr always emits it, defaulting to `text/html`. Emitting it unconditionally would change every response, and the contract allows additive optional fields only.
- **Per-request proxy comes from the `proxy` field in the request body**, not Byparr's `X-Proxy-*` headers. Contract again.
- **playwright-captcha only ever runs on a throwaway page.** Preparing a solver injects an init script that rewrites `Element.prototype.attachShadow`, and a Cloudflare interstitial will not clear while that patch is present. Measured: cleared in 3.1s without it, never in 40s with it, while a Turnstile widget filled its token in 4.5s with it and never without. Playwright cannot remove an init script, hence the second page. Byparr reached the same conclusion from the other direction and removed the solver outright (`3dcf529`), keeping it lazy first because "ClickSolver.prepare() patches attachShadow, which is what escalated a self-clearing challenge into a checkbox in the first place" (`61db8d8`). Solverr still constructs one, for the paid escalation only.
- **Firefox's COOP/COEP prefs are left on.** Byparr disables both (`f97e3d3`), because with them on Cloudflare's challenge iframe lands in an isolated content process where Juggler sees no docShell, so `content_frame()` raises and the widget's iframe never appears in `page.frames` at all (measured on one site: eight presses land with the prefs off, none with them on). Not taken. Real Firefox ships those policies on, so turning them off is a divergence on the request Cloudflare inspects hardest, and it was measured against the solver-based code that `61db8d8` then replaced: Byparr's own current path clicks a container in the light DOM and never touches the frame tree, so nothing there needs the prefs any more. Solverr's click path does the same as a fallback (see Taken), which is what makes them unnecessary here too.
- **Sessions, the reaper, and per-host engine memory are Solverr-only.** Byparr launches a browser per request.
- **Detection lists are shared across both engines** from `src/detection.py`, carrying FlareSolverr's full title and selector sets. Byparr has a single challenge title and no access-denied handling.
- **Base image is `python:3.14-slim-bookworm`**, not Byparr's `ubuntu:24.04`. No effect on solving.
- **CSP headers are left alone.** Playwright's Firefox transport runs `page.evaluate` as a main-world `eval()`, so a page whose CSP omits `unsafe-eval` blocks it (Chromium's CDP path is exempt, which is why the Chrome engine never sees this). Byparr used to strip the CSP headers off every document with `route.fetch` + `route.fulfill`, which sends the main document through Playwright's HTTP stack rather than Firefox's, changing the TLS and HTTP/2 fingerprint on the request Cloudflare inspects hardest, and forced them to track the final URL by hand because Juggler only routes the first request of a redirect chain. They removed it in `ecf7c03` and measured the cost it had been paying: through `/v1` on the same host, the stripping build offered 52 cipher suites and the build without it 16, which is what real Firefox offers. Solverr never had it. Its own code does not need it either: the user agent is read once on the blank page at context start, and every read against a challenge page (title, selectors, the token, the widget rect) goes through Playwright's isolated world or the protocol, neither of which is an `eval`. Two mechanisms were measured on 2026-08-08 against the one place CSP did bite, playwright-captcha's shadow-root traversal, and neither helped: the `security.csp.enable=False` launch pref does not disable enforcement on Firefox 151 at all, and header stripping does not reach the policy that blocks, which belongs to the cross-origin Turnstile iframe rather than the page. Solverr solved that by not needing eval (see the widget click below), so there is nothing left to port.
- **The Turnstile checkbox is clicked by coordinate, and playwright-captcha is not in the free path at all.** playwright-captcha's traversal into the widget's closed shadow root runs `evaluate_handle` (`solvers/click/common/shadow_root.py:53-55`), which the iframe's CSP blocks, so every nudge logged "call to eval() blocked by CSP" and the widget went unsolved. Solverr finds the widget through the frame tree (which sees an iframe inside a closed shadow root) or through its container (see Taken), takes the box, and clicks the checkbox with `page.mouse`. All protocol-level, so no CSP applies. That also retires the throwaway click page for the free path, since nothing injects init scripts there any more, and with it the race that let a widget be declared solved before it had rendered. Byparr arrived at the same design in `61db8d8`, with one finding worth keeping: measuring the widget with `page.evaluate` makes Cloudflare reissue the challenge every few seconds, so it never clears. Nothing here evaluates against a challenge page.
- **No `/load` endpoint.** Byparr serves Open WebUI's external web loader (article extraction via trafilatura). Solverr's public surface is `/v1` plus the optional passthrough; a second content-extraction API is a different product.
- **No `maxTimeout` alias in milliseconds.** Byparr added one for FlareSolverr drop-in compatibility. Solverr is native to that contract and already reads `maxTimeout` as milliseconds.
- **`LANG` rather than a new `BROWSER_LOCALE`.** Byparr added `BROWSER_LOCALE` (`8cb5770`) because it had no language variable. Solverr inherited `LANG` from FlareSolverr, wired to Chrome's `--accept-lang` (`src/utils.py`), so a second variable would have meant one knob per engine. `LANG` now feeds both through `config.browser_locale()`. It is also normalized rather than forwarded: `invisible_core/prefs.py` only maps `_` to `-` and appends the base subtag, so a raw `LANG=en_US.UTF-8` would set `navigator.languages = ["en-US.UTF-8", "en"]` and a matching `Accept-Language`, which is a more distinctive fingerprint than leaving it unset. Values that are not language tags are dropped with a warning.
- **The browser language comes from the same lookup as the timezone.** Byparr resolves a locale from the exit country and Chrome has never resolved one at all, so with nothing configured the two engines answered in different languages (measured 2026-08-13: Chrome `en-US,en`, Camoufox `nb-NO,nb` from the same Norwegian exit), and `ENGINE_FALLBACK` made it change mid-session. Neither value was wrong; disagreeing was. `src/geo.py` now takes the exit IP out of `prepare_session_geo` and feeds it to `resolve_session_locale`, so both are derived from one address and cannot name different countries. That is one round trip behind a proxy and two on a direct connection, where the library reports no `egress_ip` (the field exists for the WebRTC override) and the locale resolver looks the address up again; the result is cached per proxy either way, so it is per process rather than per launch. That pairing is the point: the library's own `_warn_locale_fallback` comment says a locale falling back to `en-US` while the timezone resolves is "a cross-field inconsistency of exactly the kind the timezone trap exists to prevent". Chrome also gets the `tag, base` pair rather than a bare tag, since `--accept-lang` is passed through verbatim and produced a one-entry `navigator.languages` no desktop browser sends.
- **Solverr resolves the browser timezone itself, for both engines.** Byparr leaves it to `invisible_playwright`, which resolves from the exit IP on every launch inside the library. Measured on 2026-08-13 against the pinned version: an address lookup under a 15 second budget plus a 53 MB geoip download, 8 seconds cold, no caching anywhere in `invisible_core/_geo.py`, and behind a proxy `prepare_session_geo` raises on a failed lookup and takes the launch with it. Solverr resolves in `src/geo.py`, once per proxy and cached, and passes a concrete `timezone=`, which returns from `prepare_session_geo` before that fatal branch. Behind a proxy the library still makes one lookup of its own for the WebRTC override, but non-fatally. Chrome gets the same zone through `Emulation.setTimezoneOverride`, chosen over a JS patch because it moves the browser's own ICU clock and leaves nothing in the document looking rewritten, and over the `TZ` environment variable because `uc.Chrome()` exposes no per-process environment and a process-global would race concurrent launches on different proxies. FlareSolverr has no timezone handling at all, so nothing to reconcile there.
- **`STEALTHFOX_GEOIP_MMDB` is set in the image, and it is not a public API.** The geoip database is baked at build time and pinned with this variable, because `ensure_geoip_mmdb` re-checks for a newer build on every call and would download over the baked copy. The variable belongs to `invisible_core` (20.15.0, held by the exact `invisible-playwright==0.7.2` pin), so re-check the name whenever that pin moves. It is the only thing here depending on a dependency's internals.
- **`BROWSER_GEO` reads the system tzdata table, with four overrides.** Country to timezone comes from `/usr/share/zoneinfo/zone1970.tab` rather than a list kept in the repo, since a hand-kept list is how Camoufox ended up returning wrong zones (`daijro/camoufox#589`). Two things measured against the real file on 2026-08-13 that its header does not prepare you for: a row lists every country sharing a zone and only the first is the one it speaks for (crediting them all put Germany in `Europe/Zurich`, because the Swiss row sorts first), and the promise to put "the most populous timezones first" is overridden by geography for 4 of the 24 multi-zone countries, which tzdata orders east to west. `_POPULATION_ZONES` in `src/geo.py` corrects Brazil, Russia, Australia and Canada, and an override applies only when the system confirms the zone exists.
- **`BROWSER_WAIT_TIMEOUT` lives in `config.py` and falls back instead of raising.** Upstream put `get_config_browser_wait_timeout` in `utils.py` and parses with a bare `int()`, which raises on a value that is not a number. Two reasons not to copy that. It is read inside `_evil_logic`, so upstream's raise happens mid-solve, where the engine wraps it as "Error solving the challenge", the controller falls back to the other engine, and nobody learns the variable is malformed; `config._int_env` defaults to 1 instead, matching every other integer knob here. Upstream also reads it a second time at startup purely to make a bad value fatal there, and that line is unused, which this fork does not carry. The cost is that `utils.py` now diverges from upstream by one absent function on top of the `LANG` normalization, so expect that hunk when diffing.
- **The Chrome Turnstile path waits for the widget and bounds its retry loop.** Upstream's `_resolve_turnstile_captcha` (`src/flaresolverr_service.py`, unchanged through `3ae649a`) reads `TURNSTILE_SELECTORS` the instant `driver.get()` returns and then retries in a `while True` with no deadline. Both halves are wrong together, and each one hid the other: `driver.get()` returns at `readyState complete`, so a widget injected by Cloudflare's api.js is not there yet, and a request that missed it answered "Challenge not detected!" with an empty token. Measured 2026-08-25 with a bare-browser probe in the container, over four samples across two demo pages: the token input appeared 0.01s to 0.92s after `get()` returned, and never on a page with no widget. Solverr waits `_WIDGET_RENDER_SECONDS` (5, the same grace the stealth engine gives through its networkidle settle), which is what makes the unbounded loop reachable often enough to matter, so the loop now takes a deadline of `maxTimeout` minus a margin and returns `None` rather than raising. Two smaller repairs ride along because they are the same twenty lines: the token is resolved after the cookie reload rather than before it (a reload replaces the document the token described), and the input is re-located on every read rather than held across passes (a re-render raised `StaleElementReferenceException` out of the whole request). Not offered upstream, by the owner's call.
- **A cookie with no domain is anchored to the page being requested.** FlareSolverr's contract takes `{"name": ..., "value": ...}` and Selenium's `add_cookie` anchors that to the page it is on. Playwright refuses a cookie carrying neither a url nor a domain/path pair, and refuses the whole batch with it, so the stealth engine failed the entire request on the shape the README documents while the Chrome engine handled it. Byparr has no cookie-injection feature to inherit a fix from: its `cookies` field is on the response, so this is Solverr's own parity code. `_to_playwright_cookies` now fills in the request URL, which is the same behaviour Selenium gives rather than a new one. Measured 2026-08-25 against a probe whose body says whether the cookie reached the origin.
- **A malformed proxy is refused, where upstream silently drops it.** FlareSolverr tests the proxy shape with `'url' in proxy` (`src/utils.py`), which is a substring test when the value is a string, so `proxy: "socks5://host:port"` reads as having no url and the browser launches with no proxy at all while the solve still reports success. Solverr validates once in `geo.proxy_to_config`, which every path that reaches a browser funnels through, including `get_webdriver`, which calls it before it reads the dict itself. Failing closed is the divergence: the caller asked for a proxy, and both reliability and egress identity depend on getting one. Measured 2026-08-25: `socks5://1.2.3.4:9050` returned `None` (no proxy), while a string containing "url" raised a `TypeError` instead.
- **The proxy extension is removed in a `finally`.** Upstream cleans it up after a successful launch only (`src/utils.py`, the `raise e` precedes the `rmtree`), so a launch that fails leaves a temp directory holding the proxy username and password in plaintext. Launch failures are ordinary: one was reproduced on 2026-08-25 under memory pressure. The cleanup moved into a `finally` on the same `try`.
- **The `/v1` request and response logs carry no credentials.** FlareSolverr logs the whole request at INFO and the whole response at DEBUG (`controller_v1_endpoint` in `src/flaresolverr_service.py`), and the Chrome proxy URL at DEBUG (`get_webdriver` in `src/utils.py`). The request holds the proxy password, which the `/v1` route in `src/flaresolverr.py` copies in from `PROXY_PASSWORD` whenever the client sends no proxy, so every request on a deployment with an authenticated proxy wrote that password to the log at the default level; it also holds cookie values and form fields, and a login form's fields are the site's own credentials. The response holds the solved cookies, any `Set-Cookie` header and the Turnstile token. All three lines now pass through `src/redact.py`, which keeps the structure, the URL and every name and replaces the values, and so does the failed-lookup `WARNING` in `geo._from_egress`, which printed the proxy server verbatim and the library's message with it (that message quotes back the credentialed URL it built). Redaction runs before the request boundary has type-checked anything, so each rule says what to do with the shapes it does not expect rather than letting them through. Deliberately left as upstream wrote it: the Chrome clearing core's own `Turnstile token:` INFO line in `_get_turnstile_token`, because that core stays mergeable with FlareSolverr and the token is single-use and short-lived.
- **The `/v1` route reads the proxy environment through `config.env_proxy()`.** Upstream reads `PROXY_URL` in `src/flaresolverr.py` itself and only checks that it is set, so `PROXY_URL=` (empty, which is what a compose file or an `.env` leaves behind) injected a proxy with no server into every request and `geo.proxy_to_config` then refused all of them. One reader means the route, the startup timezone lookup and the passthrough agree that an empty value is no proxy. This replaces upstream's block at `src/flaresolverr.py:16-18` and `58-63`, which the config takeover had deliberately left alone.
- **Challenge detection stays in `detection.py`, not playwright-captcha.** Byparr replaced its title check with `detect_cloudflare_challenge` (`8ef4c62`). That helper is Playwright-typed, so the Chrome engine could not share it, and its interstitial check is one selector (`script[src*="/cdn-cgi/challenge-platform/"]`) that Solverr already has alongside `#challenge-form` and `#challenge-stage` (`src/detection.py`). Its turnstile set adds `script[src*="challenges.cloudflare.com/turnstile/v0"]`, deliberately not taken: `TURNSTILE_SELECTORS` also serves as the token locator (`stealth_engine.py`, `chrome_engine.py`), so matching the api.js tag would set `is_turnstile` on a page with no input to read and no rendered frame to click, sending it down the click path to burn the whole `maxTimeout`. The case it would catch, a widget not yet in the DOM, is already handled by the networkidle settle and re-detect in `_navigate_and_solve`.

## Taken

- **URL scheme validation** (v1.2.1). Byparr enforces `http(s)://` at its model layer; Solverr validates in the controller before any engine sees the URL (`_validate_url`, `src/flaresolverr_service.py`). Worth knowing why it mattered: on the published 1.2.0 image a `file:///etc/passwd` request returned the file in `solution.response`, verified directly.
- **A Docker healthcheck** (v1.2.1). Byparr's shape, adapted: it honors `${PORT:-8191}` and uses the IPv4 literal, since `localhost` resolves to `::1` on an IPv6-enabled network while the server listens on IPv4 (the same trap Byparr hit in `885a24c`). FlareSolverr still has none.
- **The widget's container as a second way to measure it** (v1.4.0). Solverr located the Turnstile widget only through the frame tree, keyed on `challenges.cloudflare.com` appearing in `frame.url`. That is right for a site's own widget and unusable on Cloudflare's interstitial, whose challenge frame reports an empty URL to the parent, which is also why playwright-captcha's own `page.frames` fallback (`solvers/click/common/shadow_root.py:186`) cannot find it. Byparr's replacement measures the nearest ancestor `div` of the token input instead, in the page's light DOM, with size guards that tell a checkbox row from a full-page wrapper (`src/challenge.py`, `61db8d8` and `d0b0130`); they measured it clearing three live interstitials that had never cleared before. Taken as a fallback after the frame path rather than instead of it, since the iframe is the exact rect where it exists. The reads are bounded too (`426aae4`): Playwright's 30 second default would have spent a whole solve on one element.
- **Confirming that a cleared challenge stays cleared** (v1.4.0). Cloudflare drops the challenge markup while it issues the next round, so the wait loop's first clear reading was not the end of the challenge, and believing it handed back an intermediate challenge page. Byparr hit the same thing and re-checks after a delay (`challenge_is_gone`, `61db8d8`); the local evidence for it was a request that logged four distinct `__cf_chl_tk` tokens. The controller's `looks_like_challenge_html` had been masking this by falling back to the other engine, so the cost was a wasted engine attempt unless stealth was last in the order, where the challenge page reached the client.
- **Not pressing a checkbox that already carries a token** (v1.4.0). Byparr measured that pressing over the top of Cloudflare's verification restarts it, and two sites sat on "performing security verification" for a full 300s budget while being pressed a dozen times (`1a2cf32`). Also from there: a landed press earns a cooldown, a press that found nothing to hit does not.
- **The stealth browser from PyPI, pinned exactly.** Byparr moved `invisible-playwright` off a git dependency to a PyPI floor of `>=0.6.1` (`a0c4b1d`, `e298eb8`) and its lock now resolves 0.7.2. Solverr followed to `==0.7.2` (v1.4.0), which pins `invisible-core==20.15.0` outright; `STEALTHFOX_GEOIP_MMDB`, `prepare_session_geo`, `resolve_session_locale`, `ensure_geoip_mmdb` and the `locale`/`timezone` launch arguments were all re-checked against it and are unchanged, as is the `_` to `-` locale normalization that `config._language_tag` exists to get ahead of. Solverr pins exactly rather than to a floor, for the reason the original commit pin existed: this package carries the patched Firefox, so an unattended bump changes solving behavior while the build stays green. A floor is not a pin, which is why moving it is a release with a live check attached rather than a dependency bump. That commit pin was never as reproducible as it looked either: it fixed `invisible-playwright` at 0.3.0 but left `invisible-core` to float.
- **Reading the Turnstile token off the value property** (v1.4.0). Byparr reads it with `input_value` (`challenge.py`), which is `element.value`; Solverr read it with Playwright's `get_attribute`, which is `element.getAttribute` and so returns the `value` content attribute. Taken, but for a narrower reason than it first looked: the expectation was that a token assigned to `input.value` never reaches the attribute, and measured against the live widget on 2026-08-18 both reads returned the same token, so the old read was not broken for Cloudflare's own widget. It is broken for a token the paid escalation injects, which playwright-captcha assigns to the property alone (`appliers/applyCloudflareTurnstile.js`). Parity with Selenium's `get_attribute`, which returns the property, is the rest of the reason. **No user-visible effect on the free path**, so no CHANGELOG entry.

- **Cookies read after `waitInSeconds`, on both engines** (v1.6.0). FlareSolverr moved its cookie read below the wait and the screenshot (`3ae649a`) so a page that sets cookies from its own JavaScript during that wait is not read too early. Solverr had the same defect twice, once per engine (`chrome_engine.py`, `stealth_engine.py`), because the two were written against each other. Fixed in both. `returnOnlyCookies` never waits, so it is unaffected either way, and the read stays outside that branch so it still returns cookies. `test_cookies_set_during_the_wait_are_returned` in `src/test_engine_conformance.py` now pins it for both engines with one test, driving each through a fake whose jar changes while the wait runs.
- **A single reusable focus helper in the Chrome turnstile loop** (v1.6.0). `_get_turnstile_token` prepended a fresh `<button>` to the document on every failed attempt (`bc4d136`), so each retry added another stop to the tab order and `tabs_till_verify` stopped reaching the checkbox after the first pass. Upstream's fix taken verbatim: one id, remove the previous one first, and near-transparent with `pointer-events: none` so it cannot cover the page. Chrome only, since the stealth engine clicks by coordinate and never tabs.
- **`BROWSER_WAIT_TIMEOUT`** (v1.6.0). Upstream made its hardcoded one-second `SHORT_TIMEOUT` configurable (`716451b`) for slow hosts and slow sites. Taken for the Chrome engine with two divergences, below. Not extended to the stealth engine: it has no fixed per-attempt wait to parameterize, it polls `_detect_settled` every `_POLL_SECONDS` until the request's own deadline, and its neighbouring constants (`_CHALLENGE_CONFIRM_SECONDS`, `_NETWORKIDLE_MS`, `_CLICK_COOLDOWN_SECONDS`) are measured values tuned to that loop. A knob that only parameterizes one clearing core's own loop falls under the clearing-core decline rather than write-once (owner ruling, 2026-09-11, recorded in `.claude/rules/engine-layer.md`), and the README documents it as Chrome only. Safe against the budget because the whole Chrome solve runs inside `func_timeout(timeout, ...)`, so a larger value slows the retry cadence without outrunning `maxTimeout`.

## Known gaps, not yet taken

- **The paid CAPTCHA API path still depends on main-world `eval`.** It injects its token with `page.evaluate` (`captchas/*/apply.py`), which the Turnstile iframe's CSP blocks under Firefox, so the escalation cannot land a token even when the service returns one. Only fires when `CAPTCHA_SOLVER` and `CAPTCHA_API_KEY` are set. The free click path had the same problem and no longer uses playwright-captcha at all (see the divergence above).

## When you take something

1. Decide where it lands, per `.claude/rules/engine-layer.md`. A change to either clearing core is compared and ported against its upstream file. A change to a surface the seam-depth table marks Done (assembly, orchestration, sessions, config, the request boundary) is ported as behaviour into the spine, never back into upstream's per-engine shape.
2. Port it, adapting to the contract constraints above. A change a client can observe lands for both engines in the same commit, or cites the mechanism one engine genuinely lacks and records it here as a divergence. A rule both engines must hold gets one case in `src/test_engine_conformance.py`, seen failing before the fix.
3. Add the CHANGELOG entry as usual.
4. Update the audited-through row here, and add a deliberate-divergence entry if you took part of a change but not all of it.
